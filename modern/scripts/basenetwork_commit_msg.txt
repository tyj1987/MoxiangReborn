Phase 7.1 gap-fill: [Lib]BaseNetwork build script -> VS17/Win32 + sibling _full.txt log

Phase 7.1 commit eb58017 delivered the [Lib]BaseNetwork CMakeLists.txt
+ the working DLL (99840 bytes), but the build script
(modern/scripts/build_basenetwork.py) used the Ninja generator instead
of the Phase 7.2 convention: Visual Studio 17 2022 + -A Win32. The
Ninja generator skips the Win32 toolchain (which is required because
BaseNetwork uses __asm int 3 / __declspec(naked), x86-only constructs —
see KNOWN_BUGS.md Bug C-10) and produces a different build-dir layout
(no .sln, no .vcxproj). This commit realigns the build script with
the convention established by build_net.py / build_filestorage.py.

Changes
- modern/scripts/build_basenetwork.py: switch -G Ninja to
  "-G Visual Studio 17 2022 -A Win32"; mirror the
  build_net.py / build_filestorage.py pattern (write a sibling
  build_basenetwork_full.txt log next to the script for offline
  inspection).
- modern/scripts/build_basenetwork_full.txt: full MSBuild log
  captured from the script (new artifact, 11,849 bytes).

Verification
- Re-ran build_basenetwork.py after the script change. Output:
    errors: 0 | warnings: 17 | rc: 0
    Release\BaseNetwork.dll: 99840 bytes
    Release\BaseNetwork.exp:  1554 bytes
    Release\BaseNetwork.lib:  1572 bytes
  The DLL byte count matches the Phase 7.1 baseline (99840). 17
  warnings: 14x C4819 codepage (MBCS source contains chars not
  representable in codepage 936 — the legacy source uses KR/CN
  comment bytes, expected behavior under _MBCS) + 2x C4996
  inet_addr deprecation (network.cpp:85,239 — already-covered
  legacy winsock API) + 1x tool noise. No new errors.
- The CMakeLists.txt itself was already committed in eb58017 and
  is unchanged — no source files in [Lib]BaseNetwork were
  touched (per AGENTS.md "1:1 复刻" rule).

Phase 7.2 deliverables that depended on BaseNetwork.dll are now
unblocked: [Server]Agent, [Server]Distribute, [Server]Map,
[Server]MurimNet, and 4Dyuchi* engines all link against this
DLL.
